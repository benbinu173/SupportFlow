MASTER BUILD SPECIFICATION FOR A CODING AGENT

======================================================================
0. PURPOSE OF THIS DOCUMENT
======================================================================

This document is the complete implementation brief for building SupportFlow,
a production-style, portfolio-grade, multi-tenant AI customer-support SaaS.

Treat this document as the source of truth for the project.

The objective is NOT to build a simple ticket CRUD application.
The objective is to build a serious full-stack system that demonstrates:

- Python backend engineering
- FastAPI
- PostgreSQL
- SQLAlchemy
- Alembic migrations
- Redis
- Celery
- WebSockets
- JWT authentication
- refresh-token security
- RBAC
- multi-tenant architecture
- audit logging
- search, filtering, sorting and pagination
- background processing
- AI-assisted support workflows
- RAG (Retrieval-Augmented Generation)
- semantic knowledge-base search
- real-time updates
- analytics
- Docker
- automated testing
- production deployment
- observability and security

The final application must be polished enough to demonstrate in a technical
interview and structured well enough that the repository itself communicates
good engineering practices.

Do not optimize for maximum number of features. Optimize for architectural
quality, correctness, security, maintainability and demonstrable engineering
depth.

3. WHAT MAKES SUPPORTFLOW DIFFERENT FROM THE EXISTING PROJECTS
======================================================================

Do NOT clone the existing CRM project.

Existing CRM-style work already demonstrates:

- customer management
- leads
- dashboards
- CRUD
- RBAC
- tenant isolation
- audit logs
- search
- analytics

SupportFlow should differentiate itself through the following:

A. Python-first backend

The backend must be implemented using Python and FastAPI.

Do NOT implement the backend using Node.js.

B. Asynchronous architecture

Use Celery and Redis for operations that should not block HTTP requests.

Examples:

- AI ticket analysis
- email notifications
- report generation
- SLA checks
- knowledge-base ingestion
- embedding generation

C. Real-time architecture

Use WebSockets for live ticket and notification updates.

Use Redis Pub/Sub where appropriate to distribute events.

D. AI-assisted support workflow

AI should assist human support agents rather than operate as an uncontrolled
autonomous agent.

AI functionality includes:

- ticket classification
- priority recommendation
- sentiment analysis
- conversation summarization
- suggested replies
- knowledge-base question answering

E. RAG

The organization can upload internal knowledge documents.

The system retrieves relevant knowledge before generating an AI answer.

AI answers must be grounded in organization-specific knowledge rather than
inventing company policies.

F. PostgreSQL

Use PostgreSQL as the primary relational database.

This demonstrates relational database design in addition to existing
MongoDB experience.

G. Production-oriented engineering

Include:

- Docker
- migrations
- tests
- environment configuration
- structured logging
- health checks
- rate limiting
- error handling
- API documentation
- deployment documentation


======================================================================
4. NON-NEGOTIABLE ENGINEERING PRINCIPLES
======================================================================

1. Never put secrets in source code.
2. Never commit .env files containing secrets.
3. All tenant-scoped data must be isolated.
4. Never trust organization_id supplied by the frontend.
5. Derive organization identity from authenticated user context.
6. Validate all API input using Pydantic schemas.
7. Use parameterized ORM queries.
8. Passwords must be securely hashed.
9. Access tokens must expire.
10. Refresh tokens must be handled securely.
11. AI output must be treated as untrusted data.
12. AI must not automatically send customer-facing responses.
13. Long-running work must not unnecessarily block API requests.
14. Every important business operation should be testable.
15. Database changes must use Alembic migrations.
16. Do not create unnecessary microservices.
17. Keep the architecture modular but not over-engineered.
18. Prefer clear service boundaries over huge files.
19. Do not use technologies merely for resume keywords.
20. Every major dependency must have an actual responsibility.

10. AUTHENTICATION
======================================================================

Implement:

- registration
- login
- access tokens
- refresh tokens
- logout
- password hashing
- protected routes
- inactive-user rejection

Recommended token strategy:

Short-lived access token.

Longer-lived refresh token.

Refresh token should be revocable.

Never store plaintext passwords.

Never return password hashes through API responses.

Use secure HTTP-only cookies for refresh tokens if the final architecture
supports cookie-based refresh securely.

Document the chosen authentication approach.

Add tests for:

- valid login
- invalid password
- expired access token
- invalid refresh token
- revoked refresh token
- inactive user
- unauthorized role


======================================================================
11. MULTI-TENANT SECURITY
======================================================================

This is one of the most important parts of the project.

Example:

Organization A must never retrieve Organization B's tickets.

Bad:

GET /tickets?organization_id=other-company

The backend must ignore any organization identity supplied by an untrusted
client and derive tenant context from the authenticated user.

Expected flow:

Request
  ->
JWT verification
  ->
Authenticated user
  ->
User.organization_id
  ->
Tenant-scoped service
  ->
PostgreSQL query

All relevant queries must apply tenant isolation.

Write automated security tests proving cross-tenant access is rejected.

This should be explicitly documented in the README.

12. TICKET LIFECYCLE
======================================================================

Recommended states:

OPEN
ASSIGNED
IN_PROGRESS
WAITING_FOR_CUSTOMER
RESOLVED
CLOSED

Recommended transitions:

OPEN -> ASSIGNED
ASSIGNED -> IN_PROGRESS
IN_PROGRESS -> WAITING_FOR_CUSTOMER
WAITING_FOR_CUSTOMER -> IN_PROGRESS
IN_PROGRESS -> RESOLVED
RESOLVED -> CLOSED
CLOSED -> OPEN only through an explicit reopen action

The backend must validate transitions.

Do not allow arbitrary status mutation if it violates workflow rules.

Every status transition should create a ticket event and audit record where
appropriate.

4. short-lived task/state coordination where appropriate

  ->

17. AI ARCHITECTURE
======================================================================

Do NOT tightly couple the application to one AI provider.

Create an AI service abstraction.

Example conceptual interface:

AIProvider
  - classify_ticket()
  - analyze_sentiment()
  - summarize_conversation()
  - generate_response()
  - generate_embedding()

Provider implementation can call the chosen LLM/embedding provider.

This makes the project easier to maintain and demonstrates good abstraction.


======================================================================
18. AI TICKET CLASSIFICATION
======================================================================

When a ticket is created:

1. Store ticket.
2. Queue AI analysis.
3. Worker retrieves ticket.
4. Send controlled prompt to AI.
5. Request structured output.
6. Validate AI output.
7. Store analysis.
8. Update ticket metadata.
9. Publish real-time event.

Example output:

{
  "category": "Billing",
  "subcategory": "Duplicate Charge",
  "confidence": 0.94
}

The backend must validate the returned structure.

Never assume LLM output is automatically valid.


======================================================================
19. AI SENTIMENT ANALYSIS
======================================================================

Return:

- positive
- neutral
- negative

Include confidence where supported.

Example:

{
  "sentiment": "negative",
  "confidence": 0.96
}

Use sentiment as an operational signal, not as an unquestionable fact.

The UI should make it clear that the result is AI-generated.


======================================================================
20. AI SUMMARIZATION
======================================================================

For long ticket conversations, generate a concise summary.

Example:

Customer has attempted to download their policy document three times.
The issue occurs in multiple browsers and began recently.
The customer has contacted support previously.

Store the latest summary.

Allow regeneration when the conversation changes significantly.

Avoid regenerating the summary after every tiny message if unnecessary.

59. SCALING DISCUSSION
======================================================================

The system should be designed so that API instances can scale horizontally.

Conceptually:

                    Load Balancer
                         |
              +----------+----------+
              |          |          |
            API 1      API 2      API 3
              |          |          |
              +----------+----------+
                         |
                 PostgreSQL / Redis
                         |
                 +-------+-------+
                 |       |       |
              Worker1 Worker2 Worker3

The application should avoid storing critical session state only in local
process memory.

WebSocket state must be designed with multi-instance deployment in mind.

60. WHAT NOT TO DO
======================================================================

- build everything in one Python file
- use MongoDB just because it is familiar
- add Redis without a real use case
- add Celery without background work
- make the AI autonomous
- let AI directly modify critical business data without validation
- expose organization_id as a trusted security mechanism
- store secrets in Git
- store passwords in plaintext
- skip tests
- skip migrations
- skip error handling
- skip tenant isolation tests
- create unnecessary microservices
- claim features are production-ready when they are not
- use fake AI results in the final implementation
- hardcode fake analytics as if they came from the database
